01 / FRONTEND LAYERS

The request goes down. The result comes back.

MVVM means the screen displays state while the ViewModel handles user actions. The data layer connects that ViewModel to Flask.

Compose = what the user sees

Show the login screen, mode tabs, chat messages, Memo history, selection checkboxes, and recording controls. Send taps and edits to the ViewModel.

AuthScreen · HomeScreen · ChatScreen · MemoScreen · SpeechInput

ViewModel = what happens next

Keep drafts, loading states, errors, selected Memos, and the current conversation. Start work with coroutines, then publish UiState through StateFlow.

AuthViewModel · ChatViewModel · MemoViewModel · SpeechViewModel

Repository = the data operations

Expose operations such as sign in, transcribe, send a message, save a Memo, and load history. ChatRepository also sends selected Memo IDs. Validate API results and return useful data or an error.

AuthRepository · SpeechRepository · ChatRepository · MemoRepository

Retrofit = Kotlin calls to API requests

VoiceBridgeApi.kt declares endpoints. ApiModels.kt defines request and response shapes. Retrofit creates an implementation of the interface using a dynamic proxy; Gson converts JSON.

RetrofitClient.kt connects the API interface to OkHttp.

OkHttp = send and receive HTTP

Carry requests over the network and apply timeouts. SessionInterceptor attaches the Flask Bearer token to protected backend requests.

The screen does not receive HTTP directly.

Flask JSON → OkHttp response → Retrofit models → Repository result → ViewModel updates UiState → Compose refreshes.

SessionStore

A shared helper holding the current Flask token and user in memory. The interceptor reads it when sending protected requests.

AudioRecorder

A local Android helper that records the microphone. SpeechViewModel controls it; SpeechRepository uploads the finished file.

Coroutines

Let work wait for network responses while the screen remains responsive. Repository and Retrofit network operations use suspend functions.

UiState + StateFlow

UiState describes the screen now. StateFlow delivers state changes from ViewModel to Compose.

GoogleSignInClient

AuthViewModel asks this helper to launch Credential Manager. It returns a Google ID token; AuthRepository then exchanges that proof with Flask.

HomeRoute + workspace

Connect the Chat, Memo, and Speech ViewModels to the signed-in user. Preserve drafts during mode switches and move selected Memos into a new Chat draft.

  • …/data/audio/AudioRecorder.kt; …/data/AppContainer.kt creates and connects the dependencies.

02 / GOOGLE SIGN-IN

Google proves identity. Flask creates the app session.

The Android app exchanges a Google ID token for its own Flask access JWT. That Flask token is used for Speech, Chat, and Memo.

Steps 1, 2, 5, 7 · AuthRepository

AuthViewModel calls the repository to get the challenge and exchange the Google ID token. The repository uses Retrofit + OkHttp, validates the result, and saves the Flask token and user to SessionStore.

Steps 3, 4 · GoogleSignInClient

Open Google's account chooser with Credential Manager. Include the Web client ID and nonce, then return the Google ID token.

Step 6 · Flask

api/auth.py calls auth_service.py to verify the Google token and nonce. Session logic and db.py save the user and app session.

Step 8 · SessionInterceptor

OkHttp adds this header to protected Flask requests:

Authorization: Bearer <Flask token>

Two tokens, two purposes.

Google ID token: prove who signed in.
Flask access JWT: use the app APIs. Flask checks its HS256 signature, issuer, audience, expiry, and active SQLite session.

The nonce is a one-use sign-in value, valid for 5 minutes. The Flask session lasts 24 hours by default.

Where this lives in the project
  • Android: ui/auth/AuthViewModel.kt, ui/auth/AuthScreen.kt, auth/GoogleSignInClient.kt
  • Android: data/repository/AuthRepository.kt, data/session/SessionStore.kt, data/remote/SessionInterceptor.kt
  • Flask: api/auth.py, services/auth_service.py, services/session_service.py, db.py

03 / SHARED VOICE INPUT

One recording flow feeds either mode.

Speech recognition produces editable text. The user then decides whether to send a chat message or save a memo.

Record speech

SpeechInput asks for microphone permission. SpeechViewModel starts AudioRecorder, which creates a temporary AAC / M4A recording.

Stop and transcribe

The ViewModel stops recording and passes the audio file to SpeechRepository. Retrofit and OkHttp send it to Flask POST /transcribe.

Flask returns the words

api/transcribe.py checks the session and upload. stt_service.py calls OpenAI transcription and returns text as JSON.

Review your speech → Use text

The returned words appear in an editable dialog. Use text adds the text to the current Chat or Memo draft.

Chat still needs Send. Memo still needs Review and save, then confirmation.

The ViewModel tracks the phase.

Recording → Transcribing → Review

Cancel discards the attempt. Temporary audio is removed after use, and leaving the app stops an active recording.

Where this lives in the project
  • Android: ui/speech/SpeechInput.kt, SpeechViewModel.kt, SpeechUiState.kt
  • Android: data/audio/AudioRecorder.kt, data/repository/SpeechRepository.kt, ui/home/HomeScreen.kt
  • Flask: api/transcribe.py, services/stt_service.py

04 / CHAT AND MEMO

The same text can become a question or a note.

Typed text and reviewed speech use the same draft. Each mode has its own Screen, ViewModel, and Repository.

How Chat continues a conversation

New chat: the first successful send returns a new conversation_id. History: select an existing chat, load its messages, and send the same ID with follow-up questions.

How saved Memos reach the screen

MemoRepository saves through POST /memos and loads history through GET /memos. MemoViewModel publishes the list in UiState; Compose shows notes newest first and lets the user select them.

SQLite data and the Sheet copy have separate outcomes.

If Sheets fails, the completed Chat reply or saved SQLite Memo remains available. Compose shows the copy status without discarding the result.

  • Android: ui/memo/MemoScreen.kt, MemoViewModel.kt, data/repository/MemoRepository.kt
  • Flask: api/chat.py, services/chat_service.py, api/memos.py, services/memo_service.py, services/sheets_service.py

05 / SAVED MEMOS → NEW CHAT

Choose notes, add a question, then chat.

The frontend connects the Memo and Chat modes. Selecting notes prepares a new draft; the user still presses Send to ask a question.

1. Two selection entry points

Chat: Add memos → choose notes → Start new chat.
Memo: select history checkboxes → Chat with selected memos.

MemoScreen.kt · MemoPickerDialog.kt

2. Prepare the Chat draft locally

HomeRoute passes the selected notes to ChatViewModel.startWithMemos() and switches to Chat. The unsent question is kept. Attached memos can be previewed or removed before the first Send.

HomeScreen.kt · ChatViewModel.kt · MemoContextPreview.kt

3. Send IDs through the normal API path

ChatViewModel → ChatRepository → Retrofit → OkHttp → POST /chat. The request contains the question and selected memo_ids. OkHttp attaches the Flask Bearer token.

4. Flask supplies the note contents

The server checks that all selected Memos belong to the current user_id. It reads their text from SQLite and sends the question plus reference material to OpenAI.

5. Keep the context with the conversation

Flask saves the user / AI messages and Memo snapshots in SQLite. History restores both. Reopening this Chat keeps the notes used at the start.

Sheets logs the new question only.

The attached notes are stored with the Chat in SQLite. They are not duplicated into the Sheet prompt column.

Select up to 10 notes, totaling at most 20,000 characters.

  • Android: ui/chat/ChatScreen.kt, ChatViewModel.kt, MemoContextPreview.kt, data/repository/ChatRepository.kt
  • Flask: api/chat.py, services/chat_service.py, db.py and its conversation_memos table

06 / FLASK, STORAGE, AND LOGOUT

Flask checks the session, then performs the work.

The Android networking layers call Flask. The same backend routes are used by the Python test clients.

1. Check the Flask token

require_session validates the Bearer token against its stored hash and expiry. It makes the user and session available as g.chat_session for this request.

2. Run the selected feature

STT: OpenAI transcription.
Chat: OpenAI Responses + SQLite history.
Memo: SQLite note + Google Sheet copy.

3. Return JSON to Android

Return the transcript, chat result, save receipt, or error. Retrofit converts the JSON; the Repository passes the result back to its ViewModel.

Three IDs serve different jobs.

user_id: the signed-in person.
session_id: this login session.
conversation_id: one chat thread.

ANDROID · MEMORY

SessionStore

Current Flask token and user. The token is lost when the app process ends, so the next launch requires sign-in.

FLASK · SQLITE

Login, Chat, and Memo history

Users, login challenges, session token hashes, conversations, user / AI messages, Memos, and Memo snapshots attached to chats.

instance/voicebridge.sqlite3
GOOGLE SHEET · LOGS

Submitted user text

Timestamp, SessionID, Mode, and Prompt. Mode is chat or memo. Flask writes using its service account.

Sign out · end the current session

Compose → AuthViewModel → AuthRepository → Retrofit + OkHttp → POST /auth/logout. Flask expires the current app session in SQLite.

Return to the login screen

AuthRepository clears SessionStore. The app clears its workspace and Credential Manager app state; Compose shows sign-in again. The Google account remains on the device.

History belongs to user_id, not the login session.

A later login creates a new session_id and token, while the same Google account resolves the same user_id. Saved Chat and Memo history remains available.
